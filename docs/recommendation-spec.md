# 제품 추천 받기 명세

버전 v0.1 (초안) | 2026-10-24 | 기준 문서: [K_Brand_GEO_Demo_Kickoff_20261024.md](K_Brand_GEO_Demo_Kickoff_20261024.md), [interview-guideline.md](interview-guideline.md), [cosmetics-category-spec.md](cosmetics-category-spec.md)

소비자 화면에서 제품 종류를 고른 뒤 “제품 추천 받기”를 누른 참여자에게, 대화로 조건을 모으고 그 조건으로 Claude 웹 검색 결과를 보여주는 기능의 규칙이다. 본 문서의 금액·비용·문구는 검증용 가정이며 구현 완료 실적이 아니다.

## 1 위치와 우선순위

- **데모 부가 기능**이다. 착수 문서 3장의 P0 다섯 화면에 들지 않으며, API 측정 P0 경로가 끝난 뒤에 진행한다(착수 문서 14장 우선순위).
- 소비자 화면 안에서 유일하게 채팅 형식을 쓴다. 다른 화면에 별도 챗 UI를 추가하지 않는다.
- **Sieve가 직접 제품을 고르지 않는다.** 자체 제품 DB·순위·점수를 만들지 않고, 착수 문서 11장의 Claude 웹 검색 수집 결과와 출처를 그대로 보여준다.

## 2 흐름

```
제품 종류 선택 → [제품 추천 받기]
  → ① 조건 대화 (지침 기준 인터뷰, mode=recommend)
  → ② 조건 확정 요약
  → ③ 질문 조립 → ④ Claude 웹 검색 수집 → ⑤ 분석·검증
  → ⑥ 결과 화면 (후보·비교 이유·출처)
  → ⑦ (선택) “무엇을 샀는지 나중에 알려주기” → 구매 과정 공유 흐름
```

### 2.1 조건 대화

- 질문 순서·문장·분류는 [interview-guideline.md](interview-guideline.md)를 따른다(코드가 순서, Claude가 문장).
- `mode=recommend`에서는 니즈 슬롯만 묻는다: `trigger`, `concern_codes`, `skin_guide_answer`, `current_status`, `dissatisfaction`, `decision_factors`, `primary_concern_code`, `budget_band`, `planned_channel`. AI 공유 슬롯(`ai_service`, `ai_question_raw`, `ai_candidates_raw`, `verify_channels`, `intent_scale`, `leading_candidate_raw`)은 `not_asked`다.
- **답하는 방법:** 모든 질문에 글로 답할 수 있다. 보기가 **4개 이하**인 질문만 버튼을 함께 보여준다. 5개 이상이면 버튼 없이 글로만 받고 Claude가 코드로 분류한다. 순위 질문은 보기 수와 관계없이 글로만 받는다. 숫자 척도는 숫자를 적게 한다.
- 건너뛰기는 정상 답변이다(`skipped`).

### 2.2 조건 확정

추천 질문에는 **코드로 확정된 값만** 쓴다.

| 쓰는 값 | 출처 슬롯 |
| --- | --- |
| 대표 고민 → 구매 의도 ID | `primary_concern_code` (명세 3장 매핑) |
| 피부 타입 | `concern_codes`의 피부 타입 코드, `skin_guide_answer` |
| 피할 성분 | `avoid_fragrance`, `avoid_ethanol` |
| 원하는 사용감 | `feel_nonsticky`, `feel_light` |
| 예산 구간 | `budget_band` |
| 구매처 | `planned_channel` |

쓰지 않는 값: `review_required=true`인 값, 자유 입력 원문(`other`, `avoid_other`의 글), 참여자가 직접 말한 브랜드명. 요약 화면에서 참여자에게 확정 조건을 보여주고 확인을 받은 뒤 수집한다.

### 2.3 질문 조립

- 대표 의도 ID에 해당하는 **질문집 12장의 문장**(접두문 포함)을 바탕으로 하고, 나머지 조건은 고정 템플릿 문장으로 덧붙인다. Claude가 질문을 새로 쓰지 않는다.
- 예(English, US): “Among Korean-brand toners available to buy in the US, compare lightweight products suited to oily skin. Avoid fragrance. Budget: $15–25. I plan to buy on Amazon. Name 3 candidates and explain why you compared them.”
- 대표 의도가 없으면(`skin_unknown`·`other` 등) 접두문 + 조건 템플릿 + 접미문만 쓴다.
- 조립한 질문 문장, 사용한 조건 코드, `prompt_hash`, 템플릿 버전을 저장한다. 같은 조건이면 같은 질문이 나와야 한다.

### 2.4 수집

- 착수 문서 11장 **수집용 시스템 프롬프트를 그대로** 쓴다. 웹 검색 도구는 기본형 `web_search_20250305`를 쓴다(동적 필터링형은 답변에 인용이 붙지 않아 구매 링크를 만들 수 없었다). max_uses는 **5**(11장 초기값 3에서 조정: 2026-10-24 실측에서 3회 한도로 구매처 상품 페이지를 찾지 못함).
- 검색 위치와 답변 언어는 화면 언어를 따른다: English → `US`, 한국어 → `KR`.
- 자사·경쟁사 목록, 상품 사실 카드, 캠페인 후원 브랜드 정보는 **넣지 않는다**.
- 제한 시간 90초, 일시 오류 재시도 최대 2회, 429는 Retry-After 준수(11장).

### 2.5 분석·검증

- 착수 문서 11장 **분석용 프롬프트**로 제품 언급, `recommended/discouraged/neutral/uncertain`, 근거 구간, 목록 순서를 뽑는다.
- 코드로 검증한다: 근거 문장이 원문에 그대로 있는가, 인용 ID가 API가 준 목록에 있는가, 열거형·범위가 맞는가. 실패한 항목은 결과 화면에 표시하지 않고 검수 대기로 남긴다.
- 원본 JSON·sha256은 불변 저장하고 판정은 따로 둔다(착수 문서 8장). 추출 규칙이 바뀌면 다시 수집하지 않고 재분석한다.

## 3 결과 화면

| 요소 | 규칙 |
| --- | --- |
| 제목 | “Claude 웹 검색으로 찾은 후보”. “Sieve 추천”, “당신에게 맞는 제품”처럼 Sieve가 보증하는 표현 금지 |
| 후보 | 답변에 나온 후보와 비교 이유. 순서가 우열이 아니면 그 안내를 표시 |
| 출처 | 각 주장 옆에 API 인용 메타데이터의 URL만. http/https만 허용. 검색 결과에만 있던 URL과 구분 |
| 미확인 정보 | 답변이 “확인되지 않음”으로 구분한 내용은 그대로 표시 |
| 가격 | 확인일·판매처와 함께. 단정 표현 금지(질문집 11번 형식). 답변 원문에 그대로 있는 가격 구간만 표시하고, 없으면 “확인된 가격 없음” |
| 구매 링크 | 분석이 고른 판매 페이지 **인용 URL**(API 인용 메타데이터)만. 추적·제휴 매개변수(utm_*, tag, ref 등)는 지운다. 없으면 링크 없이 출처만 표시 |
| 사진 | 구매 링크 페이지의 공개 메타 태그(og:image·twitter:image). 서버가 http/https·공개 주소만 접근(내부 주소 차단, 리다이렉트마다 재검사, 6초·512KB 제한). 못 찾거나 열리지 않으면 “사진 없음” |
| 수집 조건 | 수집 시각, 모델, 검색 위치, 검색 실행 여부. 캐시를 새 응답처럼 표시하지 않음 |
| 조건 요약 | 결과에 쓴 확정 조건을 함께 표시 |

금지:

- 효능·피부 적합성 판단(“지성 피부에 맞아요”), 효과 예측(“끈적임이 줄어요”).
- **제휴 링크·캐시백·특정 상품 혜택.** 혜택 노출 전후 분리(착수 문서 4장)를 지키기 위해 결과 화면에는 넣지 않는다.
- 근거 없는 성분·용량·가격·효능 자동 완성(착수 문서 7장).

실패 표시: 검색 실패·시간 초과·`search_used=false`·검증 통과 후보 0개는 각각 그대로 알리고 “다시 시도”를 준다. 저장된 다른 응답이나 예시로 채우지 않는다.

### 3.1 결정(2026-10-24): 검색으로 확인하지 못해도 후보를 보여준다

웹 검색으로 판매 페이지를 찾지 못해 후보 0개로 끝나는 일이 잦아, 조건에 맞는 후보를 항상 보여주기로 했다.

- 수집 프롬프트에 “검색으로 다 확인하지 못해도 후보 3개를 제시하고, 확인하지 못한 내용은 밝혀라”를 덧붙인다(가격·URL은 검색으로 확인한 것만).
- 웹 검색 수집이 실패하거나 후보가 0개면 **검색 없이** 한 번 더 수집한다. 이 결과는 `source_mode=knowledge`로 저장하고 화면 상단에 “Claude가 알고 있는 정보로 고른 후보”라고 알린다.
- 후보 이름·비교 이유가 답변 원문에 없으면(분석 단계가 지어낸 경우) 계속 뺀다. 피하라고 한 제품도 뺀다.
- 검색 인용이 없는 후보는 “웹 검색으로 확인되지 않음” 표시를 붙이고 가격은 숨긴다.
- 구매 링크 순서: 인용된 판매 페이지 → 검색 결과에 있던 판매 페이지 → 참여자가 고른 구매처의 **검색 링크**(예: 쿠팡에서 제품명 검색). 상품 URL을 지어내지 않는다. 사진은 실제 판매 페이지에서만 찾는다.
- 조립한 질문 문장은 참여자 화면에 보여주지 않는다. 적용한 조건만 태그로 보여준다(질문 문장은 저장·API에는 남김).

## 4 보상

**결정(2026-10-24): 추천 받기에도 조사 보상을 준다.**

조건 대화로 모은 니즈(계기·고민·현재 제품의 아쉬움·고르는 기준·예산·구매처)는 브랜드가 알고 싶어 하는 구매 전 정보이므로, 구매 과정 공유와 같은 성격의 조사 참여로 본다.

| 항목 | 규칙 |
| --- | --- |
| 지급 조건 | 조건 대화의 필수 슬롯을 모두 처리(답 또는 건너뛰기)하고 조건 요약을 확인함 |
| 재원 | 브랜드의 **조사 예산**. 제휴 수입과 섞지 않는다(착수 문서 2장) |
| 금액 | 검증용 가정. 구매 과정 공유의 참여 보상과 같은 체계로 캠페인별 책정, 미국 캠페인은 달러 |
| 결과와 무관 | 추천 결과를 열었는지, 후보를 샀는지, 어떤 브랜드를 골랐는지와 관계없이 같은 금액 |
| 횟수 | 캠페인당 참여자 1회. 같은 참여자의 재요청은 결과는 보여주되 보상은 없음 |
| 검수 | 지급 전 검수. 무성의 답(전 슬롯 건너뛰기 등)·중복 계정·기기는 반려하고 사유를 알림. 검수 기준을 사전 공개 |
| 한도 | 캠페인 참여 인원·보상 총액 한도에 포함. 한도 도달 시 신규 보상 대상 마감 |
| 지급 | P0에서는 지급하지 않고 “내부 테스트” 표시만. 실제 지급·보상 원장은 P1 |

구매 과정 공유와의 관계: 추천을 받은 참여자가 이후 ⑦에서 결과·이유를 제출하면 다른 참여자와 같은 **완료 보상**을 받는다. 추천 보상과 완료 보상은 같은 조사 예산에서 나가며 각각 Reward 행으로 남긴다(funding=research).

## 5 데이터와 집계

- **별도 계열.** `mode=recommend` 인터뷰와 추천 수집 결과는 다음과 섞지 않는다.
  - 소비자 제출(자기보고) 집계: 참여자가 스스로 쓴 AI의 추천 사례가 아니다.
  - API 테스트 추천률: 사용자 조건이 붙은 질문이라 질문집 버전이 다르다(착수 문서 5장 비교 가능성).
- 니즈 슬롯 값은 “추천 요청 참여자 n명의 조건”으로 따로 집계할 수 있다. 표본 수·모집 경로·기간·내부 테스트 여부를 함께 표시한다.
- ⑦로 구매 과정 공유를 이어가면 그 기록의 AI 추천 출처는 **Sieve가 실행한 Claude**다. `ai_service=ai_sieve_claude`로 표시하고, 참여자가 직접 쓴 AI 사례와 같은 지표로 묶지 않는다.

## 6 비용

- 1건 = 수집 1회 + 분석 1회. 착수 문서 10장 가정(누적 입력 6,000·출력 1,000토큰, 검색 2회 / 분석 입력 2,000·출력 300토큰)으로 약 $0.06. 조건 대화의 질문 생성·분류 비용은 [interview-guideline.md](interview-guideline.md) 1장 기준으로 별도.
- 실패·재시도 비용도 기록한다. 착수 문서 10장의 데모 한도(누적 $20 경고, $50에서 새 작업 중지)에 추천 호출을 포함한다.
- 단가는 실행 전 실제 모델 기준으로 다시 확인한다.

## 7 API

| API | 입력 또는 반환 | 처리 책임 |
| --- | --- | --- |
| POST /api/interviews | lang, market, product_category, **mode=recommend** → 인터뷰 | 니즈 슬롯만 묻기. 조사 집계에서 제외 |
| POST /api/interviews/:id/answer | turn_id, kind(option/text/skip) | 지침 3.2 규칙 |
| POST /api/recommendations | interview_id → recommendation_id (202) | 확정 조건 추출, 질문 조립, 작업 생성. 같은 인터뷰 중복 요청 방지 |
| GET /api/recommendations/:id | 상태, 질문 문장, 조건, 후보·근거·인용, 수집 조건 | 검증 통과 항목만 반환. 실패 상태 구분 |
